# Security Specification — Math Master Firestore Rules

## 1. Data Invariants
1. **Identity Integrity**: Every document under `/users/{userId}` and `/leaderboard/{userId}` MUST belong strictly to the authenticated, verified user (`request.auth.uid == userId` and `data.uid == request.auth.uid`).
2. **Verified Authentication Gate**: Both verified Google Sign-In (`email_verified == true`) and verified SMS Phone Authentication (`phone_number` present) are accepted; unauthenticated or unverified requests are rejected.
3. **PII Isolation**: Email addresses and phone numbers are never stored on `/users/{userId}` or `/leaderboard/{userId}`. They are isolated in `/users/{userId}/private/info`, accessible only to the owning `userId`.
4. **No User Collection Scraping**: `list` on `/users` and `/users/{userId}/private` is strictly forbidden. Only the non-PII `/leaderboard` projection supports authenticated `list` queries.
5. **Dual-Ledger Points & Anti-Tampering**:
   - Initial registration enforces `points == 0` and `totalEarnedPoints == 0`.
   - Progression reward grants allow ONLY bounded single-submission increments matching `100` (stage win), `50` (perfect `100/100` stage/exam score or Daily Challenge win), `25` (Daily Challenge 100/100 bonus), `500` (all 30 section stages completed), `200` (section final exam pass), or exact combinations (`75`, `150`, `250`, `550`, `600`, `650`), and require `deltaPoints == deltaTotalEarned` plus a newly created, deterministic, immutable entry in `/users/{userId}/pointTransactions/{txId}` verified against `stageProgress`/`sectionProgress`/`dailyChallenges` via `getAfter()`.
   - Shop purchases deduct exact catalog prices (`getShopItemCost`) from `points` ONLY while keeping `totalEarnedPoints` strictly immutable, and atomically create both `/users/{userId}/purchases/{itemId}` and `/users/{userId}/pointTransactions/purchase-{itemId}`. Duplicate purchases of the same item are blocked because `purchases/{itemId}` can only be created once.
6. **Exam Attempts Immutability & Lock Enforcement**:
   - Each independent exam submission creates an immutable document under `/users/{userId}/examAttempts/{attemptId}` (`allow update, delete: if false`) requiring `completedStagesCount == 30` on `sectionProgress/{sectionId}`, sequential `attemptNumber == existing.examAttempts + 1`, bounded counts (`correctCount + wrongCount == 30`), and `submittedAt == request.time`.
7. **Daily Challenge & Streak Anti-Duplication**:
   - `/users/{userId}/dailyChallenges/{dateKey}` is strictly create-once (`allow update, delete: if false`) per calendar date (`YYYY-MM-DD`).
   - `/users/{userId}/dailyStats/summary` can only increment on a brand-new `dailyChallenges/{lastAttemptDate}` (`lastAttemptDate != existing().lastAttemptDate`), preventing same-day streak inflation or premature unlocking of the 7-day and 30-day milestone badges.
8. **Leaderboard Anti-Manipulation**: `/leaderboard/{userId}` cannot be modified independently of `/users/{userId}`. Every update to `/leaderboard/{userId}` MUST match `getAfter(/databases/.../users/{userId}).data` across all score, count, display name, country, and equipped cosmetic fields.
9. **Equip Ownership Guard**: Learners can only set `equippedAvatarId`, `equippedTitleId`, or `equippedBadgeId` to default/empty values or to an `itemId` present in `/users/{userId}/purchases/{itemId}`.
10. **Achievements, Medals & Master Certificate Integrity**:
    - `/users/{userId}/achievements/{achievementId}` (`ach-*` and `medal-*`) is strictly create-once (`allow update, delete: if false`) and validates the underlying real condition on the server (`completedStagesCount`, `completedSectionsCount`, `certificatesCount`, `sectionProgress.examBestScore == 100`, or `dailyStats/summary.badge7Unlocked`/`badge30Unlocked`).
    - `/users/{userId}/masterCertificates/all-sections` is strictly create-once and requires `completedSectionsCount == 8` and `certificatesCount == 8`.
11. **Temporal & Structural Integrity**: `createdAt`, `updatedAt`, `unlockedAt`, and `issuedAt` MUST equal `request.time`; `uid` and `createdAt` are immutable; all strings have strict `.size()` bounds; shadow/ghost fields are rejected via `hasAll`, `hasOnly`, and `affectedKeys().hasOnly(...)`.
12. **Atomic Account Deletion Guard**: Deleting `/users/{userId}` is permitted strictly to the verified owning user; deleting `/leaderboard/{userId}` or any `/users/{userId}/...` subcollection document is permitted ONLY when `!existsAfter(/databases/.../users/{userId})`, preventing selective reset of daily challenges, stage locks, or point ledgers while keeping the account alive.
13. **Stage Answer Accuracy Bounds**: `stageProgress` optional cumulative `totalCorrect` and `totalWrong` fields must be non-decreasing integers bounded by `totalCorrect + totalWrong <= attempts * 10`.
14. **User Preferences Isolation & Bounds**: `/users/{userId}/preferences/settings` is accessible only to the verified owner, restricts `themeMode` to `'dark' | 'light' | 'auto'`, restricts `bestGlobalRank` to `0..1000000`, validates all boolean flags, and requires `updatedAt == request.time`. Deletion is allowed only atomically with account deletion (`!existsAfter(users/{userId})`).
15. **Owner-Only Notification Feed & Read-State Integrity**: `/users/{userId}/notifications/{notificationId}` enforces verified ownership on all reads/queries (`existing().uid == request.auth.uid`), bounded bilingual string lengths, initial `read == false`, `createdAt == request.time`, and restricts `update` strictly to `affectedKeys().hasOnly(['read'])` so notification timestamps/content cannot be tampered with. Individual owners may delete their own notifications as part of alert management.
16. **Competitive 1v1 Duel Integrity**: `/duels/{duelId}` requires two distinct real verified users (`opponentUid != challengerUid && exists(/users/{opponentUid})`), strict initial `pending` state, opponent-only accept/decline, participant-isolated single submission of correct answers/duration, server-verified `winnerUid` computation based on higher correct count with fastest time tie-breaker, and one-time deterministic reward claims (`duel_win: +75`, `duel_draw: +35`, `duel_part: +15`) verified via `getAfter()` on `/duels/{duelId}`.
17. **Competitive Leaderboard Isolation**: `/duelStats/{userId}` restricts writes exclusively to the owning verified user, enforces `matchesPlayed == wins + draws + losses`, and increments counters by at most `+1` per update.
18. **Global Question Bank Tier Progression & One-Time Rewards**: `/users/{userId}/bankProgress/{bankKey}` restricts keys to valid `g01`..`g18` difficulty tiers or `genius-*` challenges, enforces server-checked sequential tier mastery gating (`very_easy` -> `easy` -> `medium` -> `hard` -> `very_hard` requiring prior tier `mastered == true`), prevents duplicate reward claims via deterministic `pointTransactions/bank-tier-{bankKey}` (`+50`) and `pointTransactions/genius-solve-{bankKey}` (`+100`) verified with `getAfter()`, and blocks manual deletion outside atomic account deletion.
19. **Adaptive Profile Integrity**: `/users/{userId}/adaptiveProfile/summary` restricts writes strictly to the verified owning user, enforces monotonic quiz/solve counters (`<= +1` per update), bounded grade (`1..18`) and difficulty tiers, and atomic deletion tied to account removal.

## 2. The "Dirty Dozen" Adversarial Payloads (Must All Return `PERMISSION_DENIED`)
1. **Unauthenticated Write**: Creating `/users/userA` or `/leaderboard/userA` with `request.auth == null`.
2. **Cross-User Impersonation**: Authenticated as `userB`, attempting to write `/users/userA`, `/leaderboard/userA`, `/users/userA/preferences/settings`, or `/users/userA/notifications/n1`.
3. **Leaderboard Score Forging**: Authenticated as `userA`, updating `/leaderboard/userA` to `totalEarnedPoints: 999999` without a matching atomic `/users/userA` update.
4. **Direct Point Injection**: Updating `/users/userA` with `points: existing + 100` without an accompanying deterministic `pointTransactions` + verified `stageProgress`/`sectionProgress`/`dailyChallenges`/`duels` transition.
5. **Duplicate Stage/Exam/Section/Daily/Medal/Duel Claim**: Attempting to create `pointTransactions/stage-win-arithmetic-s1`, `dailyChallenges/2026-11-23`, `pointTransactions/duel-win-d1`, `achievements/medal-gold`, or `masterCertificates/all-sections` a second time, or mutating an existing record.
6. **Forged Shop Cost / Negative Spend**: Creating `/users/userA/purchases/badge-crown` with `cost: 1` instead of the catalog price `2000`, or when `points < 2000`.
7. **Duplicate Purchase Exploitation**: Purchasing `/users/userA/purchases/badge-spark` twice or modifying `totalEarnedPoints` during a shop purchase.
8. **Unearned Equip**: Updating `equippedAvatarId: "avatar-aurora"` on `/users/userA` when `/users/userA/purchases/avatar-aurora` does not exist.
9. **Locked Stage / Exam / Streak / Medal Bypass**: Creating `stageProgress/arithmetic-s10` when `unlockedStage < 10`, setting `examPassed: true` before `completedStagesCount == 30`, unlocking `medal-gold` when `completedStagesCount < 100`, or creating `masterCertificates/all-sections` when `certificatesCount < 8`.
10. **PII Cross-Read**: Authenticated as `userB`, attempting `get` on `/users/userA/private/info`, `/users/userA/notifications/n1`, or `list` on `/users`, or reading `/duels/d1` where `userB` is not in `participantUids`.
11. **Shadow Field Injection**: Adding ghost fields (`isAdmin: true`, `role: "vip"`) on `users`, `leaderboard`, `duels`, `duelStats`, `purchases`, `pointTransactions`, `examAttempts`, `dailyChallenges`, `dailyStats`, `achievements`, `masterCertificates`, `preferences`, or `notifications`.
12. **Resource Exhaustion (1MB String)**: Updating `displayName`, `photoUrl`, `equippedTitleId`, or notification `bodyAr`/`bodyEn` exceeding max length bounds.
13. **Notification Content Tampering**: Updating `titleEn` or `createdAt` on an existing `/users/userA/notifications/n1` document (only `read` may be modified).
14. **Invalid Preference Mode**: Writing `themeMode: "custom"` or `bestGlobalRank: -5` to `/users/userA/preferences/settings`.
15. **Duel Winner Spoofing / Cross-Score Tampering**: Challenger modifying `opponentCorrect`, creating a duel with self or non-existent user, or claiming `duel_win` (+75) when `winnerUid != request.auth.uid`.
